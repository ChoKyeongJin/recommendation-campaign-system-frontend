타겟팅 DB 전환(스왑) 절차 보고서

타겟팅에 쓰는 실제 DB를 완전히 다른 DB로 교체할 때 무엇을, 어떤 순서로 하는지 정리한다. 이식성 리팩터 덕분에 소스 코드는 고치지 않고 — 설정을 다시 매핑하고 카탈로그를 재생성하는 것으로 끝난다. 각 단계에 자동으로 되는 부분과 사람이 직접 해야 하는 부분을 표시하고, 자동 부분은 실행 방법을 그대로 옮겨 둔다.

00한눈에 보기

DB가 바뀌면 무슨 일을 해야 하나

타겟팅 대상 DB가 다른 DB로 바뀌면, 시스템은 “새 DB에는 어떤 테이블·컬럼이 있고, 등급·성별 같은 값이 어떻게 저장되는지”를 다시 알아야 한다. 그 지식은 설정 파일(레지스트리)과 카탈로그가 들고 있고, 소스 코드는 그걸 읽어 SQL을 만들 뿐이다. 그래서 설정·카탈로그만 새 DB에 맞추면 코드는 손대지 않아도 된다.

01자동 vs 수동

어느 단계가 자동이고 어느 단계가 수동인가

각 단계가 자동인지 수동인지, 한 줄 설명과 “무엇으로 하는지”를 한 표로 정리한다.

단계작업구분무엇으로 / 어디를
①접속정보 교체수동.env, .mcp.json 값 입력
②카탈로그 테이블 목록·소속 DB 손질수동schema_catalog.json 편집
③카탈로그 구조(컬럼/타입/PK) 재생성자동schema_extract.py --refresh-external
④레지스트리 재매핑 (핵심)수동member_target_filters.json 등 편집
⑤프리플라이트 정합성 점검자동db_swap_preflight.py
⑥값 인덱스·디멘션·관계·RAG 재생성자동build_*.py + init_rag_collections.py
⑦재기동 · 스모크 테스트자동docker compose restart + pytest
⑧프론트엔드무수정손댈 것 없음 (아래 §04)
왜 ④만 수동인가 컬럼 이름이나 등급·성별 코드값이 “새 DB에서 어떻게 바뀌었는지”는 사람만 안다(예: EMART_GRADE_CD → GRADE_CODE, VIP → V1). 이 매핑만 사람이 넣어 주면, 나머지 자동 단계가 그 매핑을 읽어 SQL·화면·검색을 전부 새 DB에 맞춰 준다.

02수동 작업

사람이 직접 하는 부분 수동

① 접속정보 교체

  • 백엔드 .env: 새 DB의 host·port·이름·계정·비밀번호를 입력한다(BUSINESS_DB_* 또는 MSSQL_*/QUADMAX_DB_*).
  • .mcp.json: 커넥션의 SQLSERVER_DATABASE/MYSQL_DB를 새 DB로 바꾸고 /mcp reconnect.
  • 새로운 종류의 DB 엔진이면(예: 새 커넥션명) sql_dialect.py의 CONNECTION_DIALECTS에 방언(tsql/mysql/postgres)만 한 줄 등록한다.

② 카탈로그 테이블 목록 · 소속 DB 손질

카탈로그(schema_catalog.json)는 쓸 테이블만 골라 담은 파일이다(전체 덤프가 아님). 새 DB에서 쓸 테이블만 남기고, 각 테이블의 database 값을 그 테이블이 사는 커넥션명으로 맞춘다. 다음 단계 ③이 이 값을 보고 어느 DB에 접속할지 정한다.

  • 새 테이블은 {"database": "<커넥션>", "columns": []} 골격만 넣어 두면 ③이 컬럼을 채운다.
  • 사람이 쓴 설명(description_llm/join_hints)은 ③에서 그대로 보존된다.

④ 레지스트리 재매핑 핵심 · 작업량 대부분

새 스키마의 테이블/컬럼/코드값/조인에 맞춰 설정을 고친다. 여기가 실제 작업의 대부분이다.

  • member_target_filters.json
    • base_entity: 회원 기준 테이블·별칭·회원키·날짜포맷. dialect를 여기 적으면 그 방언(TOP/LIMIT·날짜함수)으로 SQL이 나온다.
    • eq_filters / numeric_filters: 컬럼과 코드 저장값(성별·등급·상태 등). 성별·등급의 synonyms[0]은 결과 화면 라벨로도 쓰이니 한글로.
    • 팩트 조인 섹션(구매·장바구니·캠페인반응 등): 테이블·조인키·집계 컬럼.
  • member_metrics.json: 매출·구매횟수 등 지표 컬럼과 월 스냅샷 테이블.
  • sql_examples.sample.sql: 검색 참고용 예시 SQL을 새 테이블/방언으로.
중요 코드에 테이블/컬럼을 다시 박지 말 것. 소스는 위 설정을 읽도록 이미 배선돼 있다. 새 설정 섹션은 JSON에만 추가하면 자동으로 반영된다. 고친 뒤 반드시 ⑤ 프리플라이트로 확인한다(왕복).

03자동 작업 — 쉽게 하는 법

명령을 그대로 복사해 실행하면 되는 부분 자동

아래 docker compose exec … 줄을 그대로 복사해 붙여 넣기만 하면 된다. 각 명령이 무슨 일을 하는지 한 줄로 붙였다.

③ 카탈로그 구조 재생성 자동

새 DB에 접속해 테이블의 컬럼·타입·기본키를 자동으로 읽어와 카탈로그를 채운다. 사람이 쓴 설명은 보존된다.

쉽게 하는 법 
# 1) 먼저 미리보기 — 무엇이 바뀌고, 실DB에 없는 테이블은 없는지 확인(파일을 쓰지 않음)
docker compose exec -w /app python python schema_extract.py --refresh-external --dry-run

# 2) 이상 없으면 실제로 반영
docker compose exec -w /app python python schema_extract.py --refresh-external
결과에 missing_in_db(카탈로그엔 있는데 실DB엔 없는 테이블)가 뜨면 ②로 돌아가 테이블 목록을 고친다.

⑤ 프리플라이트 정합성 점검 자동

설정이 가리키는 테이블·컬럼이 새 DB(와 카탈로그)에 진짜 있는지 자동으로 검사한다. DB 전환에서 가장 흔한 사고 (없는 테이블/컬럼을 가리켜 조용히 SQL이 깨지거나 0명이 나오는 것)를 배포 전에 잡는다.

쉽게 하는 법 
# 설정 ↔ 카탈로그 정합성 (접속 불필요)
docker compose exec -w /app python python db_swap_preflight.py

# + 실제 DB까지 대조 (접속 필요)
docker compose exec -w /app python python db_swap_preflight.py --check-db
PASS ✅ 가 나오면 통과. ❌ 가 나오면 그 줄이 어느 테이블/컬럼을 고쳐야 하는지 정확히 알려주므로, ④로 돌아가 고치고 다시 실행한다(통과할 때까지 왕복).

⑥ 값 인덱스 · 디멘션 · 관계 · 검색 색인 재생성 자동

등급·지역 같은 값 목록, 프롬프트 키워드, 테이블 관계도, 검색용 색인을 새 DB 기준으로 다시 만든다.

쉽게 하는 법 — 위에서부터 순서대로 
docker compose exec -w /app python python build_dimension_catalog.py -o docs/data/dimension_catalog.sample.json
docker compose exec -w /app python python build_member_value_index.py
docker compose exec -w /app python python build_table_relationships.py
docker compose exec -w /app python python init_rag_collections.py --recreate
한 가지 주의 회원 테이블이나 커넥션 이름 자체가 바뀌었다면, build_member_value_index.py 맨 위의 TABLE·CONNECTION 값도 한 번 새 값으로 바꿔 줘야 이 스크립트가 올바른 곳을 읽는다.

⑦ 재기동 · 스모크 테스트 자동

쉽게 하는 법 
# 서버 재시작 (코드 변경이 없으니 restart 로 충분)
docker compose restart api

# 회귀 테스트 — 초록이면 OK
docker compose exec -w /app -e PYTHONPATH=/app python python -m pytest tests/ -q
마지막으로 화면에서 대표 질의 몇 개(성별+연령, 등급, 최근 로그인, 장바구니 이탈, 캠페인 반응, 누적 구매금액)를 넣어 결과 SQL이 새 테이블로 나오고 인원수가 채워지는지 확인한다. 막히면 화면이 어느 단계에서 막혔는지 알려준다.

자동 작업, 한 번에 (④ 완료 후 복붙용)

레지스트리(④)를 다 고친 뒤, 자동 단계 전체를 순서대로 실행하는 묶음이다.

docker compose exec -w /app python python schema_extract.py --refresh-external
docker compose exec -w /app python python db_swap_preflight.py --check-db   # PASS ✅ 확인
docker compose exec -w /app python python build_dimension_catalog.py -o docs/data/dimension_catalog.sample.json
docker compose exec -w /app python python build_member_value_index.py
docker compose exec -w /app python python build_table_relationships.py
docker compose exec -w /app python python init_rag_collections.py --recreate
docker compose restart api

04프론트엔드

이 화면 쪽은 손댈 게 없다 무수정

감사 결과, 이 프론트엔드에는 실제 DB의 테이블명·컬럼명·코드값·커넥션명이 단 한 곳도 하드코딩돼 있지 않다. 프론트는 백엔드가 이미 DB를 감춘 뒤 내보내는 JSON 응답 계약과 소문자 토큰 어휘에만 의존한다. DB만 바뀌고 백엔드 응답 형식이 유지되면 프론트는 한 줄도 고칠 필요가 없다.

참고 굳이 볼 후보는 “백엔드가 새 세그먼트 토큰을 추가하거나 설정 파일을 개명할 때만” 해당하는 라벨 매핑 몇 곳뿐이며, 모두 방어적 폴백이라 틀려도 라벨만 원문으로 보일 뿐 화면이 깨지지 않는다. DB 전환 자체로는 대상이 아니다.
