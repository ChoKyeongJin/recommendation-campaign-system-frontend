참조문서(docs/data) 역할 및 변경 반영 가이드

docs/data 아래 파일들은 단순한 설정 모음이 아니라 자연어 → Event IR → RAG grounding → SQL → 출고 정책까지 여러 단계에 나뉘어 쓰인다. 파일마다 역할이 다르고 운영 반영 방식도 다르다. 어떤 파일이 어느 단계에서 쓰이는지, 고친 뒤 무엇을 해야 실제로 반영되는지를 정리한다.

00한눈에 보기

파일은 어느 단계에서 쓰이는가
자연어
  ↓
language / semantics / policy
  ↓
Canonical Event IR
  ↓
RAG 검색 / 값 해석 / grounding
  ↓
보강된 Event IR / Query Plan
  ↓
runtime/sql + schema
  ↓
SQL 생성 및 검증

즉 파일마다 역할이 다르다 — ① 자연어를 Event IR로 바꾸기 위한 설정, ② RAG가 검색할 지식, ③ Event IR을 실제 SQL로 바꾸기 위한 설정, ④ SQL 검증·출고 정책, ⑤ 테스트·문서·DB 관리용 자료.

전제 현재 docs/data 전체를 대상으로 하는 운영용 hot-reload API는 없다. 일부 파일만 요청할 때마다 다시 읽어 파일 교체로 반영되고, 대부분은 프로세스 캐시나 import 시점에 로드된다. 특히 여러 worker가 도는 서버에서는 worker마다 설정 상태가 달라질 수 있으므로, 명확히 실시간 반영되는 파일이 아니라면 서버 재시작을 기본으로 보는 것이 안전하다.

자연어를 canonical 개념 · 조건 · 연산자 · 시간범위로

1-1. 자연어 파싱 · 정규화 runtime/language/

02RAG 검색 · grounding

직접 검색 대상은 통합 산출물 하나다
generated/rag_knowledge_base.json

이 파일을 임베딩해 Qdrant knowledge collection에 저장하고 검색한다. rag_knowledge_base.json은 원본 설정 그 자체가 아니라 검색하기 좋은 형태로 다시 만든 통합 산출물이며, 여러 원본 데이터를 합쳐 생성된다.

RAG 지식의 원본

원본RAG에서의 역할변경 후 조치
generated/schema_catalog.json테이블 · 컬럼 · 타입 정보RAG 재적재 서버 재시작
runtime/language/normalization_rules.sample.json동의어와 canonical 표현RAG 재적재
runtime/policies/business_policies.sample.json업무 정책 설명과 근거RAG 재적재
generated/dimension_catalog.sample.json브랜드 · 카테고리 같은 dimension 정의RAG 재적재
generated/member_value_index.json실제 DB 값과 컬럼 · 저장값 연결RAG 재적재 서버 재시작
sql_examples.sample.sql유사 SQL 검색 예시RAG 재적재
build_rag_knowledge.py 내부 business terms일반 업무 용어 설명RAG 재생성 시 포함

일부 원본은 RAG뿐 아니라 런타임에서도 직접 쓰인다. 예를 들어 dimension_catalog.sample.json, member_value_index.json은 브랜드명 · 지역명 같은 사용자 표현을 실제 dimension이나 DB 저장값과 연결하는 grounding에도 사용될 수 있다.

RAG를 다시 적재하는 방법

python init_rag_collections.py --recreate
원본 데이터
  ↓
rag_knowledge_base.json 재생성
  ↓
임베딩 재생성
  ↓
기존 Qdrant knowledge collection 삭제
  ↓
새 collection 생성 및 적재
왜 --recreate 인가 단순 upsert를 쓰면 원본에서는 삭제된 노드가 Qdrant에는 남아 있을 수 있다. 운영에서는 --recreate를 권장한다.
  • 검증만: python init_rag_collections.py --validate-only
  • Qdrant 저장 없이 임베딩 생성까지 확인: python init_rag_collections.py --dry-run

RAG 재적재 후 서버 재시작이 필요한가?

Qdrant 검색만 보면 같은 collection을 다시 적재한 뒤 다음 요청부터 새 벡터를 검색할 수 있다. 하지만 API 서버는 시작할 때 rag_knowledge_base.json을 읽어 app.state.graph도 구성한다. 따라서 다음 두 상태가 동시에 존재할 수 있다.

Qdrant
→ 새 RAG 지식

API의 app.state.graph
→ 서버 시작 당시의 기존 지식

Qdrant 검색 결과만 바꾸면 되는 경우에는 재적재만으로 충분할 수 있다. 하지만 서버 내부 local graph까지 동일한 상태로 맞춰야 한다면 서버도 재시작해야 한다.

RAG 재생성 → 검증 → Qdrant 재적재 → 서버 재시작

Event IR · Query Plan을 테이블 · 컬럼 · JOIN · WHERE로

3-1. SQL 물리 바인딩 runtime/sql/

파일역할변경 후 조치
member_target_filters.json논리 조건을 실제 테이블 · 컬럼 · 코드 · 술어로 변환서버 재시작
member_metrics.json회원 단위 수치 지표와 실제 컬럼 · grain · 랭킹 기준 정의서버 재시작

member_target_filters.json은 SQL 생성에서 특히 중요한 설정이다. 회원 속성, 활동 상태, 가입일, 로그인, 지역, 구매, 장바구니, 캠페인 반응 같은 논리 조건을 실제 SQL 조건으로 변환한다.

  • base_entity
  • table_symbols
  • eq_filters
  • numeric_filters
  • aggregate_targets
  • cart_targets
주의 일부 함수는 파일을 다시 읽는 것처럼 보여도, 메인 graph_rag에서는 import 시 _MEMBER_TARGET_FILTERS와 여러 파생 상수를 만든다. 운영 중 파일만 교체하면 같은 프로세스 안에서 신 · 구 설정이 섞일 가능성이 있다. 그래서 runtime/sql/은 전체를 서버 재시작 대상으로 보는 것이 좋다.

3-2. SQL 생성과 검증에 함께 쓰는 데이터

generated/schema_catalog.json

실제 허용 테이블 · 컬럼 · 타입 · DB 방언의 기준이다. SQL을 만들 때 참고하고, 생성된 SQL을 sql_guard에서 검사할 때도 쓰며, RAG 지식의 원본이기도 하다. 따라서 변경 시 RAG 재생성 · 재적재 + 서버 재시작이 모두 필요하다.

generated/dimension_catalog.sample.json

브랜드 · 카테고리 같은 사용자 표현을 dimension ID 또는 코드와 연결한다. RAG 지식의 원본이므로 변경하면 RAG를 다시 생성 · 적재해야 한다.

generated/member_value_index.json

지역, 회원 등급 등 실제 DB에 저장된 저카디널리티 값을 확인해 정확한 SQL literal을 만든다. RAG와 런타임 양쪽에 영향을 주므로 RAG 재적재 + 서버 재시작을 권장한다.

runtime/external/external_region_mapping.json

외부 지역명을 CRM에 실제 저장된 지역 형식으로 변환한다. 변경 시 서버 재시작 대상으로 본다.

04검증 · 출고 정책

SQL을 만드는 게 아니라 결과를 어떻게 처리할지 정한다

runtime/policies/shipping_policy.sample.json은 SQL 자체를 만드는 파일이 아니다. SQL 검증 과정에서 finding이 발생했을 때 최종 결과 처리 방식을 결정한다.

SQL 생성
  ↓
검증
  ↓
finding 발생
  ↓
shipping_policy
  ├─ 정상 출고
  ├─ 경고와 함께 출고
  └─ 실행 차단

경로 기반 캐시가 있으므로 변경 후 서버 재시작이 안전하다.

05참고용 vs 권위

SQL을 설명하지만 compiler의 직접 설정은 아닌 파일들

table_relationships.md

테이블 간 JOIN 관계를 설명하는 생성 문서다. 현재 deterministic SQL compiler가 이 Markdown을 직접 읽어 JOIN을 결정하지는 않는다. 실제 JOIN과 SQL 물리 바인딩의 권위는 주로 member_target_filters.json, audience_catalog.json, 코드 레지스트리에 있다. 따라서 이 문서만 고쳐도 운영 SQL은 바뀌지 않는다.

sql_examples.sample.sql

RAG 유사 SQL 검색이나 LLM SQL fallback에서 참고할 수 있는 예시다. deterministic compiler에서 실제 테이블 · 컬럼을 결정하는 권위 설정은 아니다. 변경 시 서버 재시작은 필요 없지만, RAG 검색에 반영하려면 다시 적재해야 한다.

business_policies.sample.json

업무 정책 설명과 RAG 문맥 제공 성격이 강하다. 실제 CRM 타겟 SQL의 물리적 조건은 주로 member_target_filters.json, member_metrics.json, runtime/sql/metrics/*.json이 담당한다.

09운영 주의사항

덮어쓰기와 worker 불일치

JSON 파일은 직접 덮어쓰지 않는 것이 좋다

서버가 파일을 읽는 순간 JSON을 덮어쓰면 아직 작성이 끝나지 않은 중간 상태를 읽을 수 있다.

정상 JSON
→ 파일 덮어쓰기 시작
→ 요청에서 파일 읽기
→ 불완전한 JSON 읽음
→ parsing error
권장 방식 임시 파일에 새 JSON 작성 → JSON 검증 → 작성 완료 → 기존 파일과 원자적으로 교체

여러 worker 환경에서는 재시작이 더 중요하다

한 worker는 새 설정을 읽고 다른 worker는 이전 캐시를 들고 있으면 요청마다 결과가 달라질 수 있다. 명확한 hot-reload 대상이 아닌 설정을 바꾼다면 전체 worker가 동일한 버전을 쓰도록 재시작 배포하는 것이 안전하다.

  • 요청마다 다시 읽는 파일이면 파일 교체만 한다.
  • 캐시되거나 import 시 로드되는 설정이면 서버를 재시작한다.
  • RAG 원본을 바꿨다면 init_rag_collections.py --recreate로 다시 적재한다.
  • DB DDL을 바꿨다면 별도로 migration 또는 DDL을 실행한다.

RAG와 서버 내부 상태를 모두 확실히 맞춰야 하는 변경이라면 가장 안전한 배포 순서는 다음과 같다.

설정 파일 변경
→ 파일/스키마 검증
→ RAG 지식 재생성
→ Qdrant 재적재
→ 서버 재시작
→ 동작 검증
기억할 것 현재 docs/data 전체에 대한 운영용 hot-reload 기능은 없다. 반영 방식이 명확하지 않은 설정 변경은 서버 재시작을 포함한 배포로 처리하는 것이 가장 안전하다.
